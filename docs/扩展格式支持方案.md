# 电子书格式扩展方案说明

> 本文档为架构分析与实施指引；需要扩展新格式时，请阅读本文档。

## 1. 现状架构回顾

当前阅读器的解析链路是一个**分发器 + 多个独立解析器**的结构，职责清晰、解耦良好：

```text
渲染进程按钮 / 拖拽
        │  window.readerAPI.openFile / openFilePath
        ▼
主进程 ipc.ts ── 按 extname 分发 ──┬─ .txt  → txtParser.parseTxtFile()
                                   └─ .epub → epubParser.parseEpubFile()
        │  返回统一的 ParsedBook
        ▼
渲染进程 reader store → ReaderView 渲染（只依赖 ParsedBook，不关心来源格式）
```

关键事实：**渲染层完全不感知格式**。它只消费 `ParsedBook { chapters: Chapter[] }`，
`Chapter { title, paragraphs: Paragraph[] }`，`Paragraph { type, text }`。
因此**新增任何格式，只要产出符合 `ParsedBook` 结构，UI 零改动**。

## 2. 统一契约（扩展的边界）

所有解析器必须实现如下签名（参考 `txtParser.ts` / `epubParser.ts`）：

```ts
// 每个解析器文件导出同名函数，返回统一的 ParsedBook
async function parseXxxFile(filePath: string): Promise<ParsedBook>
```

`ParsedBook` 定义见 `src/shared/types.ts`，其中：

- `format`：必须是 `BookFormat` 联合类型的成员
- `chapters`：有序章节数组，`paragraphs` 内 `type` 仅允许 `heading | text | empty`
- `filePath`：必须填源文件绝对路径，进度记忆以此 key 关联

只要满足上述契约，新格式就与现有透明渲染、目录、进度保存、穿透等能力**天然兼容**。

## 3. 新增一种格式的 5 个标准步骤

以"支持 PDF"或"支持 MOBI"为例，标准扩展路径：

### 步骤 1：扩展类型白名单

`src/shared/types.ts` 的 `BookFormat` 联合类型增加新成员：

```ts
export type BookFormat = 'txt' | 'epub' | 'pdf'   // 新增 'pdf'
```

> 渲染进程未对 format 做 switch 分支渲染，仅用于文案/调试，因此通常无需改 UI。

### 步骤 2：新增独立解析器文件

在 `src/main/parsers/` 下新建 `xxxParser.ts`，实现 `parseXxxFile(filePath)`，
内部把格式专有结构（如 PDF 页、MOBI 记录）转换为 `Chapter[] / Paragraph[]`。

- 需要第三方库则在 `package.json` 的 `dependencies` 增加（如 `pdfjs-dist`、`mobi`）。
- 遵循项目规范：所有 `async/await` 包 `try-catch`，失败抛错由调用方转 `OpenFileResult`。

### 步骤 3：在分发器接入

`src/main/ipc.ts` 的 `extname` 分发链（约 24-30 行）追加分支：

```ts
const book =
  ext === '.txt'  ? await parseTxtFile(filePath)  :
  ext === '.epub' ? await parseEpubFile(filePath) :
  ext === '.pdf'  ? await parsePdfFile(filePath)  :   // 新增
  null
```

并 `import { parsePdfFile } from './parsers/pdfParser'`。

### 步骤 4：放开文件对话框过滤

`src/main/ipc.ts` 的 `dialog.showOpenDialog` 的 `filters`（约 75 行）追加扩展名：

```ts
{ name: '电子书文件', extensions: ['txt', 'epub', 'pdf'] }
```

> 拖拽打开走 `extname` 分发，无需单独处理，第 3 步已覆盖。

### 步骤 5：验证

- 复用 `tests/parser.test.mjs` 模式：生成样本 → 断言 `chapters`/`paragraphs` 结构正确。
- 跑 `npm run typecheck` 与 `npm run build` 确认三端类型一致。

## 4. 常见格式的可行性与注意点

| 格式 | 难度 | 推荐库 | 关键注意点 |
| --- | --- | --- | --- |
| **PDF** | 中 | `pdfjs-dist`（纯 JS，主进程可用） | 本质是按页位图/文本流，无固定"章节"概念；需按文本块切分或靠大纲（outline）生成章节；大文件内存高 |
| **MOBI / AZW3** | 中高 | `mobi`（node 库）或 `kindleunpack` | 含 KF8/Huffman 压缩，需解压提取 HTML；图片内联需决定是否抽取 |
| **FB2**（XML） | 低 | 内置 `htmlparser2` 即可 | 本身是 XML，章节由 `<section>` 标签直接映射，最易实现 |
| **DOCX** | 中 | `mammoth` | 转 HTML 后复用 epub 的正文抽取逻辑（`extractDocument`）即可复用 |
| **MD / 纯文本变体** | 低 | 无需库 | 等同于 TXT，重写渲染时把 Markdown 转段落或交给渲染层 markdown 渲染 |
| **CBZ/漫画** | 特殊 | `jszip` + 图片 | 图文型，当前 `Paragraph` 模型只有文本，需扩展 `type: 'image'` 或新增 `imageChapters` 字段，涉及渲染层改造 |

## 5. 架构演进建议（可选）

当格式超过 4 种时，建议把"分发 if-else"重构为**注册表**：

```ts
// parsers/registry.ts
const registry = new Map<string, (p: string) => Promise<ParsedBook>>()
registry.set('.txt', parseTxtFile)
registry.set('.epub', parseEpubFile)
// 新增格式只在这里注册，ipc.ts 改为 registry.get(ext)?.(filePath)
```

收益：新增格式不改 `ipc.ts`，符合开闭原则；解析器文件自带注册逻辑，收敛改动面。

## 6. 渲染层潜在改造点（仅图文型格式需要）

当前 `Paragraph.type` 只有 `heading | text | empty`。若支持漫画/图文混排（CBZ、带图 EPUB），
需：

1. `src/shared/types.ts` 的 `ParagraphType` 增加 `image`，并给 `Paragraph` 加可选的 `src?` 字段。
2. `ReaderView.vue` 对 `type === 'image'` 渲染 `<img>`（图片经主进程读为 base64 或临时文件 URL 回传）。
3. 解析器把图片抽取为 `Paragraph { type: 'image', src }`。

纯文本类格式（PDF/MOBI/FB2/DOCX）**无需触碰渲染层**，印证了当前契约设计的扩展性优势。

## 7. 总结

- 扩展成本低：文本类新格式平均改动面 = 1 个类型枚举 + 1 个解析器文件 + 分发器 2 处（import + 分支）+ 对话框过滤 1 处。
- 渲染层零改动是核心设计红利，源于 `ParsedBook` 这一稳定契约。
- 图文类格式需小幅扩展 `Paragraph` 模型与 `ReaderView`，属可控范围。
